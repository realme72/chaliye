# Chaliye — Ride Hailing API

A backend API for a ride-hailing platform built with FastAPI, PostgreSQL, and Redis.

---

## Tech Stack

- **FastAPI** — async REST API
- **PostgreSQL** — persistent storage via SQLAlchemy 2.0 async
- **Redis** — driver geo-index, ride status cache, rate limiting, payment idempotency
- **Alembic** — database migrations

---

## Project Structure

```
app/
  core/          # DB engine, Redis client, base model, dependencies
  middleware/    # Auth (API key), request logger (trace ID), rate limiter
  enums/         # Shared enums: RideStatus, DriverStatus, PaymentMethod, etc.
  riders/        # Rider model
  drivers/       # Driver model, schemas, repository, router
  rides/         # Ride model, schemas, repository, matching service, router
  trips/         # Trip model, schemas, repository, pricing service, router
  payments/      # Payment model, schemas, repository, router
    handlers/    # Registry pattern: Cash, UPI (PhonePe/GPay/CRED/Paytm/BHIM), Card
alembic/         # Migration scripts
main.py          # App entrypoint
seed.py          # Creates sample riders and drivers for local testing
```

## Setup - steps

### Prerequisites

- Python 3.9+
- PostgreSQL
- Redis

### Install

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### Configure

Create a `.env` file:

```env
DATABASE_URL=postgresql+asyncpg://chaliye:chaliye_secret@localhost:5432/chaliye
REDIS_URL=redis://localhost:6379/0
```

### Run migrations

```bash
alembic upgrade head
```

### Seed test data

```bash
python seed.py
```

This creates 2 riders and 3 drivers (ECONOMY / PREMIUM / LUXURY) and prints their IDs and API keys.

### Start the server

```bash
python main.py
```

API docs available at `http://localhost:8000/docs`

## Authentication

Every request requires an `X-API-Key` header. Keys are generated by `seed.py` and stored in the `riders` / `drivers` tables.

In Swagger UI click **Authorize 🔒** and paste the key before making requests.

## API Endpoints

| Method | Path | Actor | Description |
|--------|------|-------|-------------|
| `POST` | `/v1/rides` | Rider | Create a ride request |
| `GET` | `/v1/rides/{id}` | Rider | Get ride status |
| `POST` | `/v1/drivers/{id}/location` | Driver | Update GPS location |
| `POST` | `/v1/drivers/{id}/accept` | Driver | Accept a ride offer |
| `POST` | `/v1/trips/{id}/end` | Driver | End trip and calculate fare |
| `POST` | `/v1/payments` | Rider | Trigger payment |

## Ride Lifecycle

```
POST /v1/rides
    │
    ▼
PENDING ──► MATCHING ──► DRIVER_ASSIGNED ──► IN_PROGRESS ──► COMPLETED
               │                │
               └────────────────┴──► CANCELLED
```

1. Rider creates a ride → status `PENDING`
2. Matching service runs in the background — searches for ONLINE drivers nearest first (2 km → 5 km → 10 km)
3. Offer sent to driver (30s window to accept)
4. Driver accepts → status `DRIVER_ASSIGNED`, trip created
5. Driver ends trip → fare calculated, status `COMPLETED`
6. Rider triggers payment

## Key Design Decisions

**Single DB session per request** — one `AsyncSession` is shared across all repository calls in a handler and committed once at the end, giving atomic transactions without a decorator.

**Redis-first reads** — driver locations are written only to Redis (not DB per ping), enabling high-throughput GPS ingestion. Ride status and auth actor are cached in Redis to avoid repeated DB queries.

**Matching** — background task using FastAPI `BackgroundTasks`. Nearest-first geo search using Redis `GEOSEARCH`. Distributed lock (`SET NX`) prevents two drivers from accepting the same ride simultaneously.

**Payment idempotency** — Redis key `payment:{trip_id}` (24h TTL) is checked first; DB fallback if TTL expired. Only successful payments are cached — failed payments are not, so retries always hit the PSP.

**Registry pattern for payments** — adding a new payment method requires only a new handler class with `@PaymentRegistry.register("METHOD")`. Cash is offline (no PSP), UPI/Card use exponential backoff retry (3 attempts).

**Rate limiting** — sliding window via Redis sorted sets, 100 requests / 60s per actor.
